# 一个良好的 SECS/GEM 模拟器，应该具备哪些功能？

结合你目前的技术方向——使用 C#、Secs4Net 开发 EAP 侧的 SECS 通信模拟器，并尝试与真实的 Stocker 或 Device 软件（Device SW）建立通信——我建议你不要一开始就追求完整的 SECS/GEM 标准实现，而是从能够连接、能够收发消息、能够模拟设备行为、能够验证异常场景这四个阶段逐步建设。

首先明确一个概念：你要开发的模拟器，实际上可以看作一个用于验证 EAP 与设备软件通信的测试工具。

## 一、先理解模拟器在整个系统中的位置

EAP（Equipment Automation Program）

上层自动化系统，负责设备调度与信息交互

HSMS / SECS-II

TCP 连接、消息传输、协议交互

Device SW（设备软件）

设备控制软件，负责设备状态、报警、作业与执行流程

你开发的模拟器可以扮演任意一侧

- 模拟 Device SW：让真实 EAP 连接模拟设备，测试 EAP。
- 模拟 EAP：让模拟器连接真实设备软件，测试 Device SW。
- 双端模拟：同时启动两个模拟端，验证协议和业务流程。

你之前提到的目标是模拟 EAP 侧，与真实的 Stocker 设备软件建立通信。这种情况下，你的模拟器首先要能充当 EAP 端；但为了后续复用，建议在架构上允许切换角色。

这里还有一个重要区别：SECS/GEM 不只是 TCP 收发字符串。HSMS 负责会话和消息传输，SECS-II 负责消息的数据结构，而 GEM 定义了设备通信行为。三者解决的问题不同，模拟器也应该分层实现。

## 二、第一阶段：最基础的通信功能

这部分是模拟器的地基。没有它们，后续所有设备状态、报警、远程控制都无从谈起。

### 1. 通信参数配置

模拟器至少应该允许用户配置以下参数：

| 参数        | 作用                          |
| --------- | --------------------------- |
| 通信角色      | Host（EAP 侧）或 Equipment（设备侧） |
| IP 地址     | 指定本地监听地址或远端设备地址             |
| TCP 端口    | 指定 HSMS 通信端口                |
| Device ID | SECS-II 消息头中的设备标识           |
| T3        | 等待 SECS 消息回复的超时时间           |
| T5        | 两次连接尝试之间的间隔                 |
| T6        | 等待控制消息响应的超时时间               |
| T7        | 等待 HSMS 连接进入 Selected 状态的时间 |
| T8        | 接收数据字节之间允许的最大间隔             |

注意：不同定时器对应不同协议阶段，不能将它们全部理解成普通的 TCP 连接超时。具体取值应根据设备接口手册和双方配置确定。

### 2. TCP 与 HSMS 连接管理

一个好的模拟器不应该只有一个“连接”按钮，而应明确显示连接的真实状态。

Not Connected

尚未建立 TCP 连接。

Not Selected

TCP 已连接，但 HSMS 会话尚未完成 Select。

Selected

HSMS 会话已选定，可以正常交换 SECS-II 数据消息。

至少应实现：

- 建立和断开 TCP 连接。
- HSMS Select / Select.rsp。
- Deselect、Linktest、Separate 等控制消息。
- 断线检测、连接超时、自动重连。
- 收到非法或不符合当前状态的消息时，正确处理异常。
- 显示 TCP 连接状态与 HSMS 会话状态，而不是只显示一个布尔值。

HSMS 的连接状态与 TCP 连接状态并不相同。连接建立后，还需要完成 HSMS 会话选择，才能正常交换数据消息。可参考 HSMS 与 SECS/GEM 的标准概述。

### 3. SECS-II 消息编解码

SECS-II 传输的是二进制编码的数据结构，不是直接通过 TCP 发送 `S1F13` 这样的字符串。

模拟器需要支持：

- Stream / Function，例如 S1F13、S1F14、S2F41。
- 消息头、System Bytes、W-Bit 等字段的解析。
- 常见数据类型，例如 `L`、`A`、`B`、`BOOLEAN`、`I1/I2/I4/I8`、`U1/U2/U4/U8`、`F4/F8`。
- 嵌套 List、空 List、空字符串、数值数组等。
- Primary 消息与 Secondary 消息的匹配。
- 对异常消息、错误数据结构的处理。

举例：EAP 发送 S1F13，设备返回 S1F14。模拟器界面可以将它们解析成人类可读的形式：

```
S1F13 W
<L
  <A "">
  <A "">
>
```

设备返回的 S1F14 则包含通信建立结果及相应的会话信息。上面只是说明数据结构的示意，实际字段应以所采用的标准版本和设备接口约定为准。

建议：优先使用 Secs4Net 已有的 HSMS 与 SECS-II 实现，不要自己从零编写二进制协议栈。 把精力放在设备行为模拟、消息记录、场景编排和测试断言上。

## 三、第二阶段：让模拟器真正能够收发消息

连接成功不等于通信功能完善。下一步要解决消息发送、接收、等待响应以及错误诊断。

### 4. 消息收发工作台

建议主界面有一个独立的消息工作台，包含以下能力：

手动发送消息

- 选择 Stream、Function。
- 编辑 SECS-II 数据树。
- 发送 Primary 消息。
- 查看对端返回的 Secondary 消息。
- 支持发送不需要正常回复的消息（具体取决于消息类型和 W-Bit）。

  消息结构查看器
- 左侧展示消息树。
- 右侧展示数据类型、值和层级。
- 可查看编码后的十六进制数据。

  实时消息日志
- 时间戳、发送/接收方向。
- SxFy、System Bytes、消息类型。
- 处理耗时、超时、异常。

例如，在模拟器里发送一个 S1F13 后，日志可以呈现：

| 时间           | 方向           | 消息      | 结果  |
| ------------ | ------------ | ------- | --- |
| 10:00:00.100 | EAP → Device | S1F13 W | 已发送 |
| 10:00:00.120 | Device → EAP | S1F14   | 已收到 |
| 10:00:00.121 | 内部           | 事务匹配    | 成功  |

这里的时间和消息只是示例。

### 5. 请求与响应管理

模拟器需要能够正确管理消息事务，而不是简单地“发一条、收一条”。

重点包括：

- 使用 System Bytes 等关联信息匹配 Primary 和 Secondary。
- 每个需要回复的事务都有独立的等待和超时管理。
- 支持多个事务同时进行，避免一个请求阻塞整个收发线程。
- 处理延迟回复、重复回复、错误回复和无对应请求的回复。
- 正确区分需要回复的消息与不需要回复的消息。
- 对 T3 超时进行日志记录和可配置的测试断言。

例如，EAP 同时查询设备状态、请求设备常数时，两笔请求可能同时在等待回复。模拟器不能假定回复一定按照发送顺序到达。

### 6. 消息持久化与查询

你之前考虑过使用 SQLite 记录全部 HSMS 消息，这个功能非常值得保留。

建议至少记录：

| 字段              | 说明                |
| --------------- | ----------------- |
| Id              | 自增主键              |
| Timestamp       | 收发时间              |
| Direction       | Send / Receive    |
| Stream、Function | 消息编号              |
| SystemBytes     | 事务关联标识            |
| WBit            | 是否要求 Secondary 回复 |
| DeviceId        | 设备标识              |
| RawBytes        | 原始编码数据，可选         |
| DecodedContent  | 解码后的消息结构          |
| DurationMs      | 事务耗时              |
| Result          | 成功、超时、拒绝或异常       |

还应该支持按时间、SxFy、System Bytes、关键字、异常类型筛选，以及导出日志。

对于高频设备通信，建议将实时收发和数据库写入解耦，使用有界队列和批量写入，避免日志数据库拖慢通信线程。

## 四、第三阶段：实现 GEM 基础设备行为

到这一步，模拟器已经能够连接和收发 SECS 消息。但它仍然只是一个协议测试器，还不能算一个好用的设备模拟器。

SEMI E5 规定消息的结构，SEMI E30（GEM）规定设备在什么情况下使用这些消息，以及应该表现出什么行为。

### 7. 通信建立与设备在线识别

建议首先支持以下基础消息：

| 消息            | 用途            |
| ------------- | ------------- |
| S1F13 / S1F14 | 建立通信及返回通信建立结果 |
| S1F1 / S1F2   | 在线识别请求与响应     |
| S1F15 / S1F16 | 请求离线及响应       |
| S1F17 / S1F18 | 请求在线及响应       |

这些消息不应只是点击按钮后返回固定数据，而应该与模拟设备当前状态关联。

例如：

1. 模拟器启动，设备处于 Offline 状态。
2. EAP 发送在线请求。
3. 模拟设备判断当前条件是否允许切换在线状态。
4. 模拟器返回相应的响应。
5. 如果状态切换成功，设备状态随之改变，并按配置产生对应事件。

这里要特别注意：具体设备支持哪些消息、是否实现某种可选 GEM 能力，需要依据设备接口手册确认，不能假定所有设备都支持全部消息。

### 8. 三类状态模型

一个较完整的 GEM 模拟器，应把设备通信状态、控制状态和加工状态分开建模。

### 通信状态

未连接

已连接

已选定

由 TCP 与 HSMS 会话过程决定。

### 控制状态

Offline

Online / Local

Online / Remote

决定主机可以通过通信接口对设备执行哪些操作。具体状态转换遵循设备实现的 GEM 状态模型。

### 加工状态

Idle

Setup

Processing

Paused

用于描述设备加工过程；实际状态及转换方式取决于设备类型和接口定义。

这里的标签仅用于说明，不代表一套适用于所有设备的完整状态定义。尤其是加工状态，不能直接把上面几个示例当成通用标准状态枚举。

在 C# 中，我建议为三类状态分别建立模型，并通过统一的状态转换服务执行检查，避免各个消息处理器直接修改全局变量。

### 9. 设备状态变量（SV）与设备常数（EC）

模拟器需要有一套可以维护的设备数据模型。

- SV（Status Variable）：描述设备当前状态，例如设备模式、当前运行状态、当前配方名称。
- EC（Equipment Constant）：描述设备配置参数，例如某个可调整的设备常数。
- DV（Data Variable）：通常用于报告某次事件或采集记录中的数据。

可以先提供以下消息：

| 消息            | 典型用途           |
| ------------- | -------------- |
| S1F3 / S1F4   | 查询状态变量         |
| S1F11 / S1F12 | 查询状态变量的名称及相关信息 |
| S2F13 / S2F14 | 查询设备常数         |
| S2F15 / S2F16 | 设置设备常数         |

每个变量最好有独立定义，而不是散落在消息处理代码中：

```
public sealed class EquipmentVariable
{
    public uint Id { get; init; }

    public string Name { get; init; } = "";

    public string DataType { get; init; } = "";

    public object? Value { get; set; }

    public string Description { get; init; } = "";
}
```

这是一个简单的 C# 数据模型示例，不是完整的 SECS-II 编码模型。

实际实现还要区分 SV、EC、DV 的语义和权限；例如只读状态变量不应因为收到写入请求就被修改。

### 10. 事件报告（Collection Event）

这是设备模拟器中非常重要的一项能力。

实际设备通常会在特定条件下产生事件，例如：

- 设备进入 Ready 状态。
- 开始执行作业。
- 作业完成。
- 发生报警。
- 设备进入故障状态。

典型的 GEM 事件上报流程是：

设备内部发生事件

例如作业完成

检查事件订阅和报告配置

CEID → RPTID → 关联变量

发送 S6F11

Collection Event Report

EAP 接收并回复 S6F12

验证接收、关联及处理结果

模拟器至少应该支持：

- 定义 CEID、RPTID 及其关联关系。
- 配置事件启用或禁用。
- 配置事件报告中包含哪些变量。
- 手动触发事件。
- 通过状态变化自动触发事件。
- 验证 EAP 是否正确收到 S6F11 并完成响应。

还要注意，事件通知、报告配置和状态变量采集是相关但不同的功能，不能仅实现 S6F11 就认为事件机制已经完整。

### 11. 报警管理（Alarm）

报警模拟不应只是一条普通消息，而应当有自己的状态和生命周期。

典型能力包括：

- 定义报警 ID、名称、描述和类别。
- 报警发生、清除。
- 查询当前激活的报警。
- 启用或禁用报警报告。
- 向 EAP 上报报警事件。
- 验证报警发生和清除是否都被正确处理。

常见消息包括 S5F1 / S5F2（报警上报及响应）、S5F3 / S5F4（报警启用控制及响应）、S5F5 / S5F6（查询已启用报警列表）、S5F7 / S5F8（查询报警列表）。

实际设备的报警行为与支持的消息集合应当以其接口定义为准。

## 五、第四阶段：模拟真实设备的业务行为

前面解决的是协议和 GEM 基础能力。对于 EAP 开发者而言，真正能提高测试效率的，是把设备的业务流程也模拟出来。

### 12. 远程命令（Remote Command）

这是你开发 EAP 时特别值得优先实现的功能。

典型消息为 S2F41 / S2F42：EAP 发送远程命令，设备返回接受或拒绝结果。

例如，可以为模拟设备定义这些命令：

| 命令示例     | 模拟行为   |
| -------- | ------ |
| `START`  | 启动作业   |
| `STOP`   | 停止作业   |
| `PAUSE`  | 暂停作业   |
| `RESUME` | 恢复作业   |
| `RESET`  | 模拟设备复位 |
| `ABORT`  | 中止当前作业 |

这些命令名称只是示例，不是 GEM 对所有设备统一规定的命令集合。

对于每个命令，模拟器应配置：

- 命令名称和参数。
- 当前状态下是否允许执行。
- 接受或拒绝的原因。
- 命令执行耗时。
- 执行成功或失败后的状态变化。
- 命令完成后触发的事件。

最重要的一点是：S2F42 返回命令被接受，不代表设备动作已经执行完成。 模拟器应把命令响应与后续设备状态变化、完成事件分开处理。

### 13. 配方管理（Recipe / Process Program）

如果设备软件涉及工艺配方，可以逐步加入：

- 查询配方列表。
- 查询配方内容或配方相关属性。
- 上传、下载配方。
- 校验配方名称和内容。
- 模拟配方不存在、格式错误、下载失败等情况。
- 模拟配方选择、配方加载和使用中的状态变化。

传统 GEM 配方管理常涉及 S7 消息，但不同设备可能实现不同的配方管理能力，部分设备还会采用更专门的配方与参数管理标准。

对于 Stocker 等物料搬送设备，配方功能未必是首要需求。你应该根据实际 Device SW 的接口手册决定是否实现。

### 14. 作业与设备运行流程

模拟器应当能够运行一套完整的、可重复的设备流程，而不是只有孤立的按钮。

例如：

1. 设备进入 Online / Remote。
2. EAP 下发开始命令。
3. 模拟设备返回接受或拒绝结果。
4. 设备进入执行中状态并上报事件。
5. 经过可配置的延迟后，模拟作业完成或失败。
6. 设备更新状态并上报完成事件。
7. EAP 查询设备状态，确认最终结果。

对于 Stocker 这种物料搬送设备，可以进一步模拟载具到达、搬送请求、搬送执行、搬送完成和搬送失败。若涉及 GEM300，则还需按设备实际支持情况考虑 E87 载具管理、E90 基板追踪、E40 Process Job、E94 Control Job 等标准。

## 六、第五阶段：一个优秀模拟器最有价值的功能——异常场景测试

如果模拟器只能模拟一切正常的情况，它的测试价值会比较有限。实际集成中，很多问题恰恰发生在通信中断、设备状态不匹配和消息处理异常时。

### 15. 异常注入（Fault Injection）

建议提供一个专门的异常测试面板。

下面是建议实现的测试用例清单。可以勾选你希望优先开发的场景。

### 通信异常

主动断开 TCP

延迟 HSMS 响应

触发 T3 超时

停止发送 Linktest 响应

模拟连接反复断开

### 协议异常

发送不符合预期的数据结构

模拟错误的事务关联

返回协议拒绝消息

模拟重复或迟到的响应

### 设备异常

设备进入 Alarm 状态

远程命令被拒绝

设备长时间不完成作业

模拟作业执行失败

状态变化与事件上报不一致

已选择 0 项

复制清单

设计这些异常测试场景

这里有两个实现原则：

1. 异常注入必须可控，例如设置延迟时间、触发次数和生效条件。
2. 区分真实协议异常与业务层异常。比如 T3 超时是事务层的等待超时，远程命令拒绝则可能是设备业务状态导致的正常响应。

另外，涉及非法 HSMS 控制消息或畸形数据包的测试，应与正常通信测试隔离，避免错误处理影响整个模拟器。

### 16. 自动化测试与测试报告

模拟器不应只能依靠人工点击操作。成熟一些后，可以把每一组操作保存成可重复运行的测试用例。

例如：

```
测试用例：设备上线与状态查询

前置条件：
  HSMS 已进入 Selected 状态
  模拟设备当前处于 Offline

步骤：
  1. EAP 发送 S1F17
  2. 检查是否收到 S1F18
  3. 等待设备进入预期状态
  4. 查询状态变量
  5. 检查返回值

验收条件：
  响应消息符合预期
  状态变化符合配置
  所有步骤均未超时
```

建议支持以下能力：

- 测试步骤串联与条件判断。
- 每一步的超时和重试配置。
- 期望消息、期望字段及状态断言。
- 测试用例批量运行。
- 失败时保留完整消息日志。
- 输出通过率、失败步骤和耗时报告。
- 自动重复运行，用于回归测试。

如果你将来需要同时验证多个 EAP 或多台设备的通信，可以进一步支持多实例和并发测试。

## 七、第六阶段：模拟器应该具备怎样的界面？

对于你的 C# / WPF 项目，我建议按以下方式划分主界面。

顶部：连接与设备配置

角色、IP、端口、Device ID、连接按钮、HSMS 状态。

设备状态面板

在线状态、控制模式、加工状态、报警。

消息发送面板

选择 SxFy、编辑数据树、发送消息。

变量与事件管理

SV、EC、CEID、RPTID、报警定义。

场景与异常测试

运行场景、注入故障、查看断言结果。

底部：实时通信日志

收发方向、消息编号、时间戳、耗时、原始数据、错误详情。

这是一种建议的布局，不必一次性全部开发。最初只做连接管理、手动收发和日志三个页面就可以。

## 八、C# 项目应该怎样分层？

我建议将通信协议、GEM 行为和 UI 分开。即使第一版只是 Console 程序，也可以采用同样的架构。

Presentation

WPF / Console · 配置、日志、手动操作

Application

场景执行、消息事务、测试断言、异常注入

GEM Domain

设备状态机、变量、事件、报警、远程命令

Communication Infrastructure

Secs4Net、HSMS、SECS-II、SQLite 日志

在你目前使用的技术栈中，可以先建立如下项目：

```
SecsSimulator.sln
├── SecsSimulator.Core
│   ├── DeviceState.cs
│   ├── EquipmentVariable.cs
│   ├── AlarmDefinition.cs
│   └── EventDefinition.cs
├── SecsSimulator.Application
│   ├── MessageDispatcher.cs
│   ├── ScenarioRunner.cs
│   └── TestAssertions.cs
├── SecsSimulator.Infrastructure
│   ├── SecsSessionService.cs
│   ├── MessageLogRepository.cs
│   └── SimulatorConfiguration.cs
├── SecsSimulator.Console
└── SecsSimulator.Tests
```

其中 `SecsSimulator.Console` 可以作为第一版入口；等核心通信逻辑成熟后，再添加 WPF 项目。

具体注意：

- 不要让 ViewModel 直接承担 SECS-II 消息解析。
- 不要让消息处理器直接修改任意设备状态。
- 消息日志与消息发送使用解耦的处理流程。
- 设备行为应当可通过配置复现。
- 业务测试尽量不依赖真实 TCP 连接，通信集成测试再单独覆盖网络层。

## 十、最后，什么才算是一个“良好”的模拟器？

我认为可以用三个标准来判断。

1. 通信正确：协议状态、消息结构、事务关联和超时处理正确。
2. 行为可信：状态转换、事件、报警和远程命令符合目标设备的接口约定。
3. 测试有效：能够复现正常与异常场景，自动判断结果，并保留足够的信息定位问题。

另外，SEMI E30 中的基础要求与可选附加能力并不相同，GEM300 也不是所有设备都必须完整实现的功能集合。模拟器的目标应该是匹配你要测试的具体设备接口，而不是盲目实现所有 SxFy 消息。
